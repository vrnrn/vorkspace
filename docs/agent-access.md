# Agent access with /operator

## Enable access

Type `/operator` at the start of a composer message to enable vorkspace access in that thread. For example, `/operator start two Codex sessions: one to inspect the API and one to review the UI`, or `/operator list my notes`. The slash picker also offers this command. The transcript shows only the request text in a translucent amber bubble; vorkspace removes the command from the request sent to the agent and supplies the local `app` CLI path and instructions on that turn. Later turns in the same thread can use the CLI without repeating `/operator`; other threads receive no CLI instructions or app access. The CLI can act only during an active agent turn. The agent can run the shown `app --help` command for the exact JSON input fields.

## CLI actions

- `models.list` shows available providers, models, settings, and permission modes.
- `sessions.start` creates a session in the caller's project (or a Bot's selected assigned project). Operator reveals a new tab by default; Bots leave it in the background. Set `reveal` explicitly to choose. By default the prompt is submitted; `draft: true` saves it unsent. It accepts `harness`, `model`, a bounded string-valued `modelSettings` object, and `runtimeMode` (`read-only`, `supervised`, `auto-accept-edits`, `auto`, or `full-access`). Omit `runtimeMode` to inherit the caller's access policy. `workspaceMode: "worktree"` creates an isolated checkout, optionally from `worktreeBase`. For an existing checkout, set `worktreeCwd` to a path returned by `worktrees.list`; the path must belong to the selected project's Git worktrees. `worktrees.create` creates a named new or existing local branch checkout. Invalid launch settings and paths fail before session creation. Use `placement: "right"` or `placement: "down"` to split beside the caller's open pane. `besideSessionId` chooses another open session pane in the same project, including one just created. Split placement reveals the result even when `reveal` is false. Closed or unrelated split targets are rejected before creation and checked again before publication; the app never chooses a replacement target silently.
- `sessions.list` shows project sessions and their archived status. `sessions.read` returns up to 40 transcript rows by default (`limit` is capped at 200), an older-row `before` cursor, and `hasMore`. `maxChars` bounds the text budget across the requested rows. `sessions.send` submits a follow-up to an idle loaded session; `sessions.draft` saves an unsent message. Both preserve an existing draft or file selection and reject busy or loading sessions. `folders.list` and `folders.move` organize project sessions in sidebar folders, including a new folder.
- `workspace.list` returns the selected project's open tabs, stable `tabId` and `paneId` values, each tab's layout and focused pane, typed resources, and sash coordinates. It also returns bounded native `availableNotes`, current inbox `availableItems`, `availableBots`, and `availableBotDocuments` with the exact IDs needed for opening, plus note/item truncation and item loading flags. `workspace.open` opens a session, Notes library or note, connector or item, Bot or Bot document, terminal, Search, To-dos, Automations, Channels, or a file. Use `kind` plus its resource field (`sessionId`, `noteId`, `provider`, `itemKey`, `bot`, `document`, or `path`). A split needs `placement: "right"` or `"down"` and `targetPaneId` from `workspace.list`; the same width and stack limits as dragging in the UI apply. `workspace.focus` and `workspace.close` take `paneId`. `workspace.move` takes exactly one of `paneId` or `tabId`, plus `targetPaneId` and `edge` (`left`, `right`, `top`, `bottom`); `tabId` moves the entire tiled tab. `workspace.detach` gives one pane its own tab at optional `index`, and `workspace.reorder` takes `tabId` and `index` to reorder the visible strip. `workspace.resize` takes a listed `tabId`, `sashPath`, `index`, and normalized `ratio`. A running terminal returns a `confirmation_required` error containing its current process; after inspecting it, send a new request ID with `confirmRunning: true` and matching `expectedProcess`. Pane IDs are scoped to the caller's authorized project and current working copy. Global app resources retain their one live editor or connector owner; commands navigate them only through the selected authorized project. Read-only Operator threads and Minions can list tabs but cannot change them.
- `sessions.stop`, `sessions.archive` and `sessions.delete` take a `sessionId` to manage another session in the project. Bots can select an assigned project with `project`. Stop cancels the current turn and pauses queued messages; archive stops and saves the conversation for later restoration; delete stops and permanently removes the conversation. Open files, terminals and worktrees are kept. These actions cannot target the caller, Bot chats, habit runs, channel workers, orchestration workers or protected internal hidden conversations. Ordinary delegated sessions remain controllable when a Bot hides them from the sidebar. Hidden sessions whose ownership cannot be verified remain protected. Ownership is checked against persisted records and again at the actual effect boundary, including deferred calls. A loading conversation is left untouched until its queue and draft are available.
- `worktrees.list` reports `locked`, `dirty`, `merged`, `unpublishedCommits`, unarchived `sessions`, and `removable` for local linked worktrees. An unavailable lock, status, or commit count is `null`. If required safety evidence is unavailable, `removable` is `false`. `worktrees.remove` takes a `path` and uses Git's non-force removal. Uncommitted or unique work, ignored files outside regenerable directories, locked worktrees, unavailable safety checks, running sessions, open terminals, and unarchived sessions block removal. Open views update through the same flow as Settings. Git can remove a fully merged branch with its worktree.
- A successful Bot management action dismisses that Bot's monitoring of the target. Other Bots' monitoring is kept; an already queued completion message remains part of its saved outbox.
- `notes.list` returns both the legacy numeric `id` and the native string `noteId` for each authorized project note. `notes.read` and `notes.write` accept either ID; `noteId` targets the exact native note, while existing numeric `id` commands remain compatible. `notes.write` creates a project note when neither ID is supplied, or updates a saved note while preserving its slug, tags when omitted, recording association and source project. An open note with unsaved editor or recording work rejects an external write, keeping its draft. A successful write refreshes clean Notes views. Bots with several assigned projects can pass `project` when creating a note.
- `todos.list`, `todos.add`, `todos.update` and `todos.remove` manage the caller's project board. Bots and Minions use their assigned projects; a Bot with several must supply `project`. Local to-dos work without GitHub. Items have `title`, `description`, `attachments` and `dependencies`; statuses are `todo`, `inProgress`, `inReview` and `done`. `before` reorders a local item within its column. GitHub issues on a linked project also appear in `todos.list`; their IDs begin with `github:`. Add with `github: true` or use `todos.publish` to create an issue. `todos.reconcile` checks an uncertain issue creation, while `todos.retry` requires `confirmNoIssue: true` after checking GitHub. `todos.cancelPublish` returns an uncertain publish to local editing only after GitHub has been checked and `confirmNoIssue: true` is supplied. `todos.reconcileEdit`, `todos.retryEdit` and `todos.discardEdit` handle uncertain remote edits with their explicit confirmation fields. See [Project to-dos](todos.md).

Bots and Minions receive the available app actions and JSON fields in their provider context. The reference uses the same catalog as CLI help and the Minion capability filter. The context explains how to read saved soul, root memory, topics, and archive through the authenticated CLI. Existing provider sessions receive the updated context when its fingerprint changes.

If a worktree setup command fails or is interrupted, its warning stays pending until a provider confirms completion of a turn that carried it. Overlapping turns or uncertain delivery can repeat the warning.

## Bot context and memory

Each Bot has a **Context compaction** choice in its General settings and during creation. A Bot can change its own policy through `bots.configure {"compactionMode":"sessionRollover"}` or `{"compactionMode":"native"}`; it takes effect on subsequent turns. Minions cannot change this policy through the CLI. **Fresh session** is the default: when saved usage reaches 80% of the context window, the next ordinary turn starts a new native provider session with a bounded conversation recap, current soul and memory. The app chat, drafts and queues remain intact. The native session ID and its usage reading are reset together before dispatch; a failed start or delayed update cannot restore the old thread's full context ring. Earlier native sessions stay in the provider's history and share the same Bot working directory.

**Native compaction** keeps the provider session and lets the provider shorten its context. `/compact` requests native compaction through the existing conversation lifecycle on Codex, Claude, Pi and OMP in either mode. For Bots, it first reconciles native history and discards a parked transport when that history changed. A durable local submission claim excludes overlapping imports and provider operations until compaction settles; the cursor checked during reconciliation must still match when the claim is acquired. Usage updates apply only to the same provider session, account and working directory. Unsupported transports report that limitation instead of silently starting a new session. Compaction preserves the app's saved transcript, queued messages and drafts.

Bot and Minion context receipts include the latest recorded compaction ID as well as the provider session ID and context fingerprint. Bots also track compaction markers read from their native Codex or Claude transcript. The receipt describes the context delivered at the start of a turn. A compaction during that turn therefore makes the receipt stale for the next turn, which reloads the current soul, memory and app instructions. Manual, failed, cancelled and interrupted compaction attempts also trigger this refresh: an unsuccessful local outcome does not prove what the provider retained. The saved tool rows and receipt preserve this behavior across app restarts. Ordinary turns reuse unchanged context. Fresh-session recovery and deliberate provider changes retain their existing conversation recap or handoff path.

Durable memory complements provider compaction. Bots are instructed to save concise, lasting preferences, decisions, constraints and reusable lessons as they learn them, using `memory.add`, `memory.replace` and `memory.remove`. Useful source references belong in the fact text; detailed notes belong in topics. Root memory supplied to the provider is bounded to 200 lines and 24 KiB; topic notes and archived facts remain available through `memory.read` and `memory.search`. Memory is editable background context, not authoritative live task state or an instruction overriding the user. Current session and project to-do status must be read from the app's records. No additional model call or automatic transcript-to-memory extraction runs during compaction.

## Bot working folders

Opening a Bot prepares `~/.vorkspace/bots/<name>` and uses it as the conversation's working directory. Each named folder is a directory symlink to its existing app-data owner, normally `~/Library/Application Support/com.vorkspace.desktop/bots/<bot-id>`. `SOUL.md` contains its standing instructions, `MEMORY.md` its root memory, and `memory/` its topics and archive. There is one copy of these files: edits through either path are visible to the app. Existing historical owners remain in place. Development databases publish under `bot-workspaces/` beside their database, outside the desktop namespace.

Names are sanitized for use as one directory component. A conflicting name receives the Bot ID as a suffix; existing foreign files and folders are never replaced. A saved home remains stable after a display-name change. Existing sessions change only their working directory, preserving provider identity, transcript, queued input and drafts. Assigned absolute project paths accompany Codex's workspace-write roots and Claude's additional directories; read-only policies remain read-only. Existing Minions and explicit worktree sessions retain their working directory; newly created Minions receive their own home but read their parent's soul and memories.

`AGENTS.md` initially points external agents to the soul and memory; later user edits are retained. Generated `SESSION.md` records the app session, assigned projects and a shell-quoted resume command for Codex or Claude, including its provider account location. It is refreshed when the Bot opens and after a managed turn. An old turn cannot overwrite a pointer belonging to a replacement app session. A pre-existing user-owned `SESSION.md` is preserved. Resume commands contain no credentials.

Provider history stays in native provider storage, such as `~/.codex/sessions` for the default Codex account, rather than being copied into the Bot folder. Use the exact command in `SESSION.md` to reopen that history. Codex's interactive picker can require `--include-non-interactive` to list app-server sessions and `--all` to include sessions whose original directory differs. See [Codex resume](https://learn.chatgpt.com/docs/developer-commands#codex-resume) and [Claude sessions](https://code.claude.com/docs/en/sessions).

Completed user and assistant messages from the current Codex or Claude session sync into the same Bot chat on open, during the existing 10-second idle refresh, and before a managed turn. The reader follows complete JSONL records incrementally; compressed Codex histories and their append tails are supported. Native identities and import receipts prevent managed messages or repeated refreshes from appearing twice. The Store commits imported rows, receipts and the read cursor together, preserving rich existing blocks, drafts and queued input. New external turns or newly observed native compaction invalidate any parked provider process so the next turn resumes the same ID from current disk state. Reading the app's own completed turns preserves its warm process.

Finish the current turn before moving between Vorkspace and an external CLI. Vorkspace defers imports while it owns an active submission and refuses a new managed turn while the native history reports an unfinished external turn. If the CLI exits without recording completion, the Bot shows **External turn unfinished** with **Resume here**. After stopping or closing that CLI, confirm the recovery to keep the same native session without resending its unfinished message. Recovery publishes the interrupted exchange's saved text before admitting another app turn, so later messages cannot overtake it. The durable acknowledgement applies only to the exact account, session and native-history snapshot; further native writes require a new confirmation. `bots.historyStatus {bot}` exposes the recovery token for an accessible peer Bot; `bots.recoverHistory {bot,expectedHistory,confirmStopped:true}` applies the same recovery after explicit confirmation from the user. Minions cannot recover another Bot. This does not lock an independently launched CLI; two frontends must not write the session simultaneously. A missing or unreadable native file leaves the saved app history intact. Tools, reasoning and sidechain messages are not imported as chat prose. App bridge controls remain available only during managed turns. `SESSION.md` points to the current native session after a fresh-session rollover.

## Persistent Bot teams

Minions require **Settings › Bots › Minions**. A parent Bot hires persistent members with roles and specialties, reuses them for later tasks, and retires them when no longer useful. Hiring itself starts no task and requires no project. These are Bot actions, not additional `/operator` permissions:

```text
minions.hire {name,role,specialties?,project?}
minions.list {}
minions.fire {minion}
minions.retry / minions.discard {minion,messageId}
minions.spawn {prompt,name?,role?,specialties?,project?,harness?,model?}
bots.list {}
bots.read {bot,before?,limit?,maxChars?}
bots.send {to,message,expectReply?}
channels.list {}
channels.create {name,topic?,members:[Bot names]}
channels.read {channel,limit?}
channels.post {channel,message,to?:[Bot names]}
```

`specialties` is an array of short strings. Optional `project` validates an assigned parent project without restricting the member to that project; execution uses the parent's live project scope. `minions.spawn` is compatibility hire plus an initial peer task. Its `harness` and `model` fields are not accepted by `minions.hire`. `minions.list` includes stable identity, role, specialties, retirement state, backing session and activity. `minions.fire` accepts an owned member's ID or unambiguous name and preserves its history.

Use `bots.send` for repeated delegation, rather than `sessions.send`. `expectReply` defaults to true, and the app returns the member's final reply automatically while the autonomous-hop budget permits it. The sender should end its turn instead of polling. Channel workers post their final reply automatically. Direct and channel routes share a four-hop budget, including when a Bot creates or reuses a channel.

A Minion's own ID remains the sender and conversation/outbox owner. Its parent ID owns shared soul and memory, while to-dos belong to the selected assigned project. Allowed Minion actions include memory/todo/notes operations, selected reads and team communication; they exclude hiring/firing, session control, worktree creation and soul/habit changes. Project-scoped reads use the parent's assignments. Peer reads, lists and sends involving a Minion are limited to its parent and siblings. Top-level Bots retain ordinary collaboration with other top-level Bots.

A channel containing Minions must remain within one team. Membership and delivery checks enforce that boundary, including automatic replies and queued work. `channels.list` returns `teamParent` and `userReadOnly` for supervision surfaces. Users can inspect member and team-channel history but cannot send messages to either; user requests go through the parent Bot. Native member views are read-only, including composer, voice and retry/resume entry points.

Retirement revokes active app admission, stops loaded execution views, clears the member's outbox, pauses saved follow-ups and cancels forbidden channel deliveries. Saved conversations remain available. Reopening validates membership and delivery receipts before resuming eligible peer work; retired work is not revived. Existing Minion project-session records migrate to protected Bot conversations while retaining their histories. See [Minions](minions.md) for the ownership and lifecycle reference.

## Mutation receipts

Every mutating command reserves its caller-scoped request ID and a fingerprint of its action and input in SQLite before applying any effect. Drafts are flushed and submitted prompts enter the existing durable message queue before completion is acknowledged. A queued prompt retains its text, mode and message ID until provider admission. Ordinary reopened session follow-ups wait for explicit review; Bot peer queues resume eligible undelivered messages through their own membership and submission checks. Completion is saved before acknowledgement. Repeating the same ID and input returns the saved result, including after an app restart; changing the action or input with that ID fails. Read queries return current state without writing receipts. If the app stops after admission and before it can save a result, that request stays unconfirmed: it may have executed, and the app never dispatches it again automatically. Inspect the affected state before deciding on a separate new command. Storage failures fail closed rather than authorizing a blind retry.

Failed launch installation cleans up its new session and view, and rolls back an unchanged local worktree still owned by that launch. Resources whose ownership changed are preserved and reported. No pane is published before its prompt or draft is durably accepted.
