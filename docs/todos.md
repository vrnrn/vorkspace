# Project to-dos and GitHub issues

Each project has a first-class local to-do board. It works without a GitHub remote, authentication, or a network connection. The personal board is separate. A to-do has a title, description, attachment references, dependency references, and one of four statuses: `todo`, `inProgress`, `inReview`, or `done`. Local rows live in `todo_items` and retain their order within a status column.

When a project's `origin` is a GitHub repository, its board also reads that repository's issues through the authenticated, bounded GitHub CLI adapter. These items carry a `github:<owner>/<repo>#<number>` ID and an `issue` reference. GitHub remains authoritative for their title, body, attachments, dependency links and state. Existing issues appear without a local import. A local to-do retains its own ID and storage owner until the user chooses **Publish to GitHub**, or a CLI caller adds it with `github: true`. Losing GitHub access leaves local to-dos available and reports the remote read error; it does not convert or delete them. At the 500-item bound, the board shows the latest 500 GitHub issues with a muted notice that older issues remain on GitHub. An actual read failure remains an error.

For issue-backed items, GitHub's closed state maps to Done. Open issues with the `vorkspace:in-review` or `vorkspace:in-progress` label map to In review or In progress; other open issues map to To do. Vorkspace creates its own status labels when needed and leaves other labels alone. Dependencies use GitHub's native blocked-by links, including links to issues in other repositories. If GitHub returns a truncated dependency list, the detail form shows that more dependencies are on GitHub, makes dependency controls read-only, and omits dependencies from title or description saves. Image and video attachments use `gh issue create/edit --attach`; paths must resolve to files inside the project, and GitHub CLI determines which media formats it accepts. HTTPS attachment references become links in the issue body. Existing GitHub attachment URLs are shown in the item details. Local to-dos can store file paths or URL references without requiring GitHub.

The board uses compact cards with a title, up to three lines of description, and dependency links. A floating **Create task** button stays at the bottom right and opens a title-entry popover; Enter submits, while Escape or Cancel keeps the unfinished title for later. The Done status uses the theme's green success icon. Clicking a card opens a centered details overlay while keeping the columns behind it. The description renders as Markdown; **Edit** opens the title, description, attachment and dependency fields in the same overlay. **Close**, Escape or an outside click returns to the board. Save and status actions stay visible while the contents scroll. The overlay fits the window, including when opened from a narrow tile. Cards support dragging between statuses and reordering local items; the details footer also moves a task through the four statuses.

The dependency selector excludes the task itself and offers only issue-backed items when editing a GitHub issue. Unfinished inputs remain in the view when the overlay closes, another task opens, or the board changes. Dependency links on cards and in details open the related task when it is on the current board. Closing an issue-backed item moves it to Done on GitHub; deleting a local item removes its local row. The personal board never attempts GitHub access.

`todos.list/add/update/remove` are available to Operator threads and Bots under their existing access policies. `todos.publish` explicitly publishes a local project item. `todos.reconcile` checks whether an uncertain create produced an issue. `todos.retry` requires a new request and `confirmNoIssue: true` after a person checks GitHub. `todos.cancelPublish` uses the same check and confirmation to return an unconfirmed draft to local editing, even if the origin is currently disconnected. The board never resubmits an uncertain create automatically. A durable local pending row carries the original repository and a private submission marker included in the issue body; a later list de-duplicates a matching issue in the view, and an explicit reconcile joins that issue to the row durably. A successful issue retains a local receipt, while the live issue replaces that receipt in a connected board view. If its initial status needs a follow-up GitHub write, the issue receipt and pending status edit commit together. Remote edits save their requested fields and last issue snapshot before a GitHub write. If a write is unconfirmed, the saved edit remains visible and blocks another write until `todos.reconcileEdit`, an explicit `todos.retryEdit` with `confirmNoEffect: true`, or `todos.discardEdit` with `confirmChecked: true`. A still-pending attempt has a bounded wait before explicit retry, so another window cannot immediately overlap it. Remote edits are never replayed automatically during disconnection.

Bots and Minions use assigned project boards. A Bot with one assigned project can omit `project`; one with several must choose a full project path. A read-only `todos.list` reports older saved Bot tasks separately as `legacyItems`. The first mutating Bot to-do command moves those rows transactionally to its sole assigned project. When several projects are assigned, the To-dos page offers an explicit **Move here** action instead. The original row IDs, details and statuses survive the move. A Bot without an assigned project keeps its saved rows until a project is chosen.
