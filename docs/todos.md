# Project to-dos and GitHub issues

Each project has a first-class local to-do board. It works without a GitHub remote, authentication, or a network connection. The personal board is separate. A to-do has a title, description, attachment references, dependency references, and one of four statuses: `todo`, `inProgress`, `inReview`, or `done`. Local rows live in `todo_items` and retain their order within a status column.

When a project's `origin` is a GitHub repository, its board also reads that repository's issues through the authenticated, bounded GitHub CLI adapter. These items carry a `github:<owner>/<repo>#<number>` ID and an `issue` reference. GitHub remains authoritative for their title, body, attachments, dependency links and state. Existing issues appear without a local import. A local to-do retains its own ID and storage owner until the user chooses **Publish to GitHub**, or a CLI caller adds it with `github: true`. Losing GitHub access leaves local to-dos available and reports the remote read error; it does not convert or delete them. At the 500-item bound, the board shows the latest 500 GitHub issues with a muted notice that older issues remain on GitHub. An actual read failure remains an error.

For issue-backed items, GitHub's closed state maps to Done. Open issues with the `vorkspace:in-review` or `vorkspace:in-progress` label map to In review or In progress; other open issues map to To do. Vorkspace creates its own status labels when needed and leaves other labels alone. Dependencies use GitHub's native blocked-by links, including links to issues in other repositories. If GitHub returns a truncated dependency list, the detail form shows that more dependencies are on GitHub, makes dependency controls read-only, and omits dependencies from title or description saves. Image and video attachments use `gh issue create/edit --attach`; paths must resolve to files inside the project, and GitHub CLI determines which media formats it accepts. The adapter checks the installed CLI for the requested upload and dependency flags before reserving a pending write; an older CLI leaves the draft editable and reports the required update. HTTPS attachment references become links in the issue body. Existing GitHub attachment URLs are shown in the item details. A description edit preserves those references when the request omits attachments. Local to-dos can store file paths or URL references without requiring GitHub.

The board uses compact cards with a title, up to three lines of description, and dependency links. A floating **Create task** button stays at the bottom right and opens a title-entry popover; Enter submits, while Escape or Cancel keeps the unfinished title for later. The Done status uses the theme's green success icon. Clicking a card opens a centered details overlay while keeping the columns behind it. The description renders as Markdown; **Edit** opens the title, description, attachment and dependency fields in the same overlay. **Close**, Escape or an outside click returns to the board. Save and status actions stay visible while the contents scroll. The overlay fits the window, including when opened from a narrow tile. Cards support dragging between statuses and reordering local items; the details footer also moves a task through the four statuses.

The dependency selector excludes the task itself and offers only issue-backed items when editing a GitHub issue. Issue choices show the repository and issue number and save a repository-qualified link. Unfinished inputs remain in the view when the overlay closes, another task opens, or the board changes. A detail draft retains the task revision from when it was opened, including while stashed. If a local task or GitHub issue changed, saving preserves the draft and offers **Discard draft and reload**. Save unfinished detail edits before publishing a local task. Publication reserves the saved revision checked during preflight and holds that row for reconciliation until the result is known. Dependency links on cards and in details open the related task when it is on the current board. Closing an issue-backed item moves it to Done on GitHub; deleting a local item removes its local row. The personal board never attempts GitHub access.

When another window or a Bot publishes a task, its local receipt keeps open and stashed drafts attached to the issue. The draft retains its opening revision. Review the published issue and reload its details before saving a GitHub edit. If another draft is already saved for that issue, the conflict action offers to open it.

`todos.list/add/update/remove` are available to Operator threads and Bots under their existing access policies. `todos.publish` explicitly publishes a local project item. `todos.reconcile` checks whether an uncertain create produced an issue. `todos.retry` requires a new request and `confirmNoIssue: true` after a person checks GitHub. `todos.cancelPublish` uses the same check and confirmation to return an unconfirmed draft to local editing, even if the origin is currently disconnected. The board never resubmits an uncertain create automatically. A durable local pending row carries the original repository and a private submission marker included in the issue body; a later list keeps that local receipt visible instead of a matching remote issue, and an explicit reconcile joins that issue to the row durably without losing its requested initial status. A successful issue retains a local receipt, while the live issue replaces that receipt in a connected board view. Publication atomically converts incoming local dependency references to the issue URL, so links keep resolving online, offline, and after restart. Subsequent local writes resolve older saved local IDs to the same issue URL. Rewriting a dependency advances its task revision, so an older editor keeps its draft and offers a reload. If its initial status needs a follow-up GitHub write, the issue receipt and pending status edit commit together. Remote edits save their requested fields and last issue snapshot before a GitHub write. If a write is unconfirmed, the saved edit remains visible on its original board and blocks writes to the same GitHub issue across project paths until `todos.reconcileEdit`, an explicit `todos.retryEdit` with `confirmNoEffect: true`, or `todos.discardEdit` with `confirmChecked: true`. A still-pending attempt has a bounded wait before explicit retry, so another window cannot immediately overlap it. If an older database has multiple saved edits for one issue, each remains available for reconciliation or explicit discard on its board. Retry requires resolving the other receipts first. Every remote edit attempt has a durable identity. Completion, reconciliation, discard and retry compare that identity, so a late result cannot clear a successor. The native app also rejects overlapping operations for the same issue or publication, including discard while a write is in flight. Remote edits are never replayed automatically during disconnection. Mutating CLI and Bot calls refresh open boards after success or failure, because a failed remote operation can still commit a local recovery receipt or legacy task migration.

Bots and Minions use assigned project boards. A Bot with one assigned project can omit `project`; one with several must choose a full project path. A read-only `todos.list` reports older saved Bot tasks separately as `legacyItems`. The first mutating Bot to-do command moves those rows transactionally to its sole assigned project. When several projects are assigned, the To-dos page offers an explicit **Move here** action instead. The original row IDs, details and statuses survive the move. A Bot without an assigned project keeps its saved rows until a project is chosen.
